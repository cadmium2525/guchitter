# 愚痴ったー 設計書

## 目的と到達範囲

短い愚痴を端末内へ残し、あとから読み返して笑える日記にする。タイムラインと 💢 のイライラボタンを中心とした独自 UI を採用し、実在 SNS のロゴ・商標は流用しない。

基盤、タイムライン、テキスト投稿、怒りカウンター、IndexedDB保存、PWAのキャッシュに加え、編集・削除、全文検索・タグ検索、並べ替え・ランキング、画像添付、暗号化完全バックアップ・追加復元を実装した。実機iPhone Safari・Android Chromeの検証は未実施で、自動テストの結果とは分けて記録する。

## 現在の画面と検索

タイムライン、検索、イライラランキング、設定の 4 画面を持つ。スマートフォンでは下部固定ナビゲーションと目立つ投稿ボタン、広い画面では左右の補助パネルを使う。投稿の編集でタグを再抽出し、作成日時と怒り値は保持する。削除は確認ダイアログの操作後に行う。

タイムラインには「新しい順」「ランダム」のタブと投稿一覧・空状態を表示する。歓迎バナー、ヘッダーの「この端末だけ」表示、常設の投稿フォームは表示しない。スマートフォンの ＋ ボタン、広い画面の投稿ボタンから、ネイティブの `dialog` を使った投稿モーダルを開く。入力欄へフォーカスを移し、閉じた後は起点のボタンへ戻す。閉じる操作や Escape で本文・怒り値の下書きを捨てず、再表示時に復元する。下書きはメモリ上だけに保持し、再読み込みやアプリ終了で失われる。

投稿カードには「端末に保存済み」のチェックと更新表示を置かず、ランキングの紹介バナーも表示しない。本文中のハッシュタグを隠し、下の色付きタグだけを表示する。保存処理の成功・失敗の判定は変えず、失敗時は入力を残してエラーを表示する。本文・怒り値・添付画像の下書きはメモリ上だけに保持する。

投稿フォームの ＃ ボタンはタグ履歴の一覧を開く。現在保存されている全投稿のタグを正規化して集計し、使用回数の多い順にすべて表示する。同一投稿内で同じ正規化済みタグを複数回使っても 1 回として数える。タグを選ぶと本文のカーソル位置へ挿入し、本文に存在するタグは選択不可にする。新しいタグを手入力する操作も設け、固定の例示タグは置かない。履歴は投稿の編集・削除を反映する派生データであり、専用テーブルや IndexedDB のスキーマ変更・データ移行は必要としない。

投稿の保存に成功すると下書きを初期化してモーダルを閉じ、通常投稿・引用投稿は新しい順のタイムラインへ、返信は該当スレッドへ移動する。保存失敗時はモーダルと下書きを保ち、エラーを表示する。ランダム順はセッション内のシードから決め、「ランダム」タブを選ぶたびにシードを更新する。同じシードではイライラ値の加算・編集・件数表示の更新で並べ直さない。

引用と返信は別の関連付けで、1投稿にどちらか1つを設定できる。引用元は本文・タグ・画像を一段だけ埋め込み、引用の引用を再帰表示しない。元投稿の編集は表示に反映する。返信は親へのIDを持ち、どの返信からでも祖先と同じ枝の返信をツリー表示する。兄弟は作成日時・ID順、ツリーは深さ優先で並べる。引用は返信ツリーの子に含めない。投稿ごとの本文・画像・タグ・怒り値は独立する。

引用元・返信先が削除されても関連投稿は削除しない。参照IDを保持し、元投稿の削除を示す。途中の返信が削除された場合、その子孫は削除済み親を起点にたどれる。ツリーの祖先探索と列挙は反復処理・訪問済みIDで循環を防ぎ、表示の字下げは最大36pxに制限する。スレッドURLは`#thread/<encoded ID>`、戻るはブラウザー履歴と元画面の検索・タグ・ランダム順・スクロール位置を使う。URLに本文は含めず、別の保存領域へ投稿を公開する機能もない。

引用元・返信先だけを選んだ状態も下書きとして更新・再読み込みの保護対象にする。閉じる操作では本文・画像・怒り値と一緒に関係も保持し、別の引用元や返信先へ切り替える前に確認する。引用・返信の解除では入力内容を残して通常投稿へ戻せる。新規保存は参照先の存在を投稿と同じIndexedDBトランザクション内で確認する。

全文検索は本文全体を対象とした端末内の部分一致検索であり、形態素解析や外部検索 API は使わない。NFKC 正規化と小文字化の後、空白区切りの複数語を AND 条件で照合する。`#タグ` は正規化済みタグとの完全一致とする。投稿内のタグボタンも同じタグ検索へ移動する。検索画面は新しい順・古い順・イライラ順の選択を持つ。新しい順・古い順は作成日時、イライラ順・ランキングは怒り値で並べる。

テーマはライト・ダーク・端末設定の3種類。`localStorage`にはテーマとバックアップ案内の間隔・保存確認日時だけを記録し、本文・画像・パスワードは保存しない。設定画面は端末内の日記が暗号化されていないこと、保存領域が消える可能性、バックアップと復元の手順を案内する。永続ストレージの要求は設定から行い、未許可でも通常の投稿処理を妨げない。

## データモデル

IndexedDBのスキーマはv3で、`posts`と`attachments`を持つ。v1からの移行では既存投稿へ空の`imageIds`を追加する。v2からv3は`quotePostId`・`replyToId`のインデックスを追加し、既存の本文・画像・タグ・怒り値・日時・IDは変更しない。

```ts
type Post = {
  id: string;
  body: string;
  tags: string[];
  imageIds: string[];
  angerCount: string;
  createdAt: number;
  updatedAt: number;
  quotePostId?: string;
  replyToId?: string;
};
```

| 項目 | 意味・不変条件 |
| --- | --- |
| `id` | 端末内で生成した投稿 ID。作成後は変えない |
| `body` | 本文。HTML として実行せず、テキストとして描画する |
| `tags` | `#` を除いたタグの配列。重複を除去し、本文から再生成できる形にする |
| `imageIds` | 表示順の画像ID。画像側の`postId`と相互に一致させる。1投稿4枚まで |
| `angerCount` | `0` または先頭ゼロのない非負の 10 進文字列。正規表現は `^(0\|[1-9][0-9]*)$` |
| `createdAt` | 作成日時。Unix epoch ミリ秒の有限かつ非負の安全な整数 |
| `updatedAt` | 最終変更日時。同じ形式で `createdAt` 以上 |
| `quotePostId` | 引用元の投稿ID。省略可能、`replyToId`との同時指定不可。削除済みIDも保持 |
| `replyToId` | 返信先の投稿ID。省略可能、`quotePostId`との同時指定不可。削除済みIDも保持 |

怒り値は保存時・JSON 化時に文字列とし、加算は各桁の繰り上がり、比較は桁数と同じ桁数内の辞書順で処理する。値全体を `Number` へ変換して計算しない。無制限とはアプリ固有の回数上限を設けない意味であり、端末の保存容量・メモリは有限である。連打は保存済み値を Dexie の読み書きトランザクション内で更新し、同時操作による増分の取りこぼしを防ぐ。最終更新時刻は端末時計が戻った場合も以前の値を下回らないようにする。

日時順は`createdAt`を基準とし、同値ではIDによる安定した規則を持たせる。イライラボタンを押しても投稿作成日時は変えない。怒り順・ランキングは任意精度で比較する。本文はtrimして保存し、本文か画像の少なくとも一方を必須とする。

IndexedDBスキーマとバックアップ形式・論理スキーマのバージョンは別管理する。移行はDexieのバージョン付きスキーマで実施する。日記の代わりに`localStorage`を使用しない。

## オフラインと更新

初回オンライン起動で HTML・JS・CSS・アイコンをキャッシュする。準備完了後はネットワークに依存せず投稿と閲覧を行う。Service Worker に日記の同期・アップロード機能は持たせない。タグ検索や全文検索の処理も端末内だけで完結する。

GitHub Pages の `/<repo>/` 配下で、Vite の `base`、manifest の `start_url`・`scope`、Service Worker の登録範囲を揃える。将来 URL に画面状態を持たせる場合は、静的ホスティングの再読み込みで 404 にならない方式を選ぶ。

更新用バナーは下書き・編集中の内容・画像処理・バックアップ入力や検証結果・書き込み処理がある間、更新操作を保留する。下書きはメモリ上の状態であり、OSによるアプリ終了からの自動復元は実装していない。キャッシュ削除とIndexedDBの日記削除を同じ操作にしない。

## プライバシーの境界

利用者の登録、有料 API、バックエンド、広告、解析、外部フォントを設けない。アプリ実行時の外部通信は静的なアプリ資材の取得・更新に限定する。ホスティングサービスが扱うアクセス情報と、端末内で扱う日記データを区別する。

現在の IndexedDB は平文保存であり、アプリのパスワードロックや端末内暗号化は初回範囲外。同じ端末・ブラウザーを操作できる人や、同じオリジンで動く他の JavaScript からの隔離を保証しない。GitHub Pages の同じ所有者の複数プロジェクトは同じオリジンを共有するため、日記専用のオリジンが望ましい。DB 名を変えるだけではセキュリティ境界にならない。

ストレージの削除や容量不足は起こり得る。永続ストレージの要求が使える場合も、許可を保証できず、バックアップの代わりにはならない。日記やバックアップの内容を例外ログ、URL、解析イベント、Git リポジトリへ含めない。

## 画像の処理

画像は端末内でデコード・縮小し、CanvasでWebP・品質0.82へ再エンコードする。変換結果のMIMEを確認し、WebP未対応時はPNG、次にJPEGへの再変換を試す。デコード不能なHEICなどはJPEG・PNGへ変換して選び直す案内を出す。原本や原本のEXIF・位置情報は保持せず、外部変換APIは使わない。SVGは拒否する。

添付は投稿と分けてIndexedDBにBlobとして保存する。モデルは`id`、`postId`、`mimeType`（WebP/JPEG/PNG）、`byteLength`、`width`、`height`、`createdAt`、`blob`。投稿の作成・画像追加、編集時の追加・保持・除去、投稿削除時の関連画像削除を両テーブルの同一トランザクションで実行する。他投稿の画像参照や重複参照を拒否し、書き込み失敗時は一部の画像や投稿を残さずロールバックする。非同期の画像バイト検証はトランザクション前に済ませる。

1投稿4枚、入力1枚20MiB以下・4,000万画素以下、出力長辺2048px以下・1枚5MiB以下。小さい画像は拡大しない。複数枚は順番に処理し、選択分に失敗があれば途中まで追加しない。入力寸法は可能な範囲でデコード前に確認し、デコード後も画素数を確認してからCanvasを確保する。保存前とバックアップ復号時に、BlobのMIME・長さ、PNG/JPEG/WebPのシグネチャ・符号化寸法と宣言値を確認する。完全な画像デコーダーによる検証ではない。プレビュー・拡大表示のObject URLと変換Canvasは不要になったら解放する。上限付近を含む実機メモリ動作は未検証である。

## 暗号化完全バックアップ

暗号化はWeb Crypto APIだけで行い、パスワード・復号済みデータ・鍵をサーバーへ送らない。UIでは12文字以上と確認入力を求める。バックアップ用パスワードをIndexedDB・localStorage・ログへ保存しない。処理終了・キャンセル時にフォームの参照を外すが、JavaScriptのメモリを完全消去できるとは保証しない。復号して確認中の内容はアプリのメモリに存在する。

### 暗号形式 v1

- エンベロープは UTF-8 JSON。識別子は `guchitter-backup`、`formatVersion` は `1`。
- KDF は PBKDF2 / SHA-256、反復回数 `600000`、出力は AES-256 用の 256 bit。初期仕様ではこの組み合わせだけを受け付け、ファイル指定の任意の高い反復回数を実行しない。
- パスワードは入力した文字列そのものを UTF-8 化する。trim や Unicode 正規化を暗黙に行わない。作成時は確認入力を求める。
- `crypto.getRandomValues` で毎回新しい 16 byte のソルトと 12 byte の nonce（IV）を生成する。
- 暗号は AES-GCM、タグ長 128 bit。`subtle.encrypt` が返す認証タグ付き暗号文を保存する。
- バイナリはパディング付き標準 Base64 で記録し、厳密に検証する。
- ソルト・nonce は秘密ではない。パスワードと導出鍵はファイルに含めない。

```json
{
  "format": "guchitter-backup",
  "formatVersion": 1,
  "schemaVersion": 3,
  "kdf": {
    "name": "PBKDF2",
    "hash": "SHA-256",
    "iterations": 600000,
    "salt": "<base64: 16 bytes>"
  },
  "cipher": {
    "name": "AES-GCM",
    "keyLength": 256,
    "tagLength": 128,
    "nonce": "<base64: 12 bytes>"
  },
  "ciphertext": "<base64: encrypted UTF-8 payload and authentication tag>"
}
```

上記の`<...>`は説明用であり、有効なバックアップではない。`schemaVersion: 3`は画像と引用・返信関係を含むpayloadの論理スキーマを表す。既存schema2のファイルもそのバージョンのAADとデータ検証を使って読み込む。未知の版を推測して変換しない。出力ファイルの拡張子は`.guchitter-backup`、MIMEは`application/json`。

ヘッダーを認証する AAD は、次の順番の値を持つ配列を `JSON.stringify` し UTF-8 化したものとする。オブジェクトのキー順への依存を避け、暗号文以外の全フィールドを含める。

```ts
[
  format,
  formatVersion,
  schemaVersion,
  kdf.name,
  kdf.hash,
  kdf.iterations,
  kdf.salt,
  cipher.name,
  cipher.keyLength,
  cipher.tagLength,
  cipher.nonce,
]
```

未知のキー、重複キー、未対応の型・バージョン・アルゴリズムは拒否する。ヘッダーのパラメーターを検証してから KDF を実行する。認証失敗は「パスワードが違うか、ファイルが破損しています」と表示し、復号・復元成功には進めない。

### 暗号化する内容と作成フロー

payloadは`schemaVersion`、`exportedAt`、全`posts`、全`attachments`を含む。タグは各投稿に含め、画像は保存済みバイト列をBase64で完全に収録する。画像ごとにSHA-256、長さ、MIME、寸法、日時、投稿参照を含める。ダイジェストは内部整合性確認に使い、認証付き暗号化の代わりにはしない。見た目の設定とリマインダー設定は含めない。

1. 投稿と画像を同じ読み取りトランザクションの一貫した snapshot として取得する。
2. 型・日時・ID・参照・画像長・ダイジェストを検証してから、payload を UTF-8 JSON へ直列化する。
3. 新しいソルト・nonce で暗号化し、出来上がったファイルを同じパスワードで復号して payload の整合性まで再確認する。
4. 復号・検証が成功した `File` だけを共有・保存に進める。読み取り、暗号化、再検証、共有のどこかが失敗した場合は失敗として表示する。
5. iPhone では `navigator.canShare({ files })` を確認し、ユーザー操作に対応する共有ボタンから `navigator.share` を実行する。未対応時は Blob のダウンロードと「ファイル」への保存案内を提供する。非同期暗号化の後で共有に必要なユーザーアクティベーションが失われる場合は、生成後に別の共有ボタンを出す。
6. 共有 UI の完了はバックアップ先での永続保存を保証しない。「作成済み」「共有操作完了」「保存確認済み」を区別し、キャンセルを成功扱いにしない。

上限を超えるファイルで端末が停止しないよう、v1 の処理上限を次のように定める。作成時も同じ上限を適用し、自分で復元できないファイルを作らない。上限はカウンター自体の回数制限ではなく、一度に扱えるファイルの制限である。超過時は切り捨てず処理を中止して理由を表示する。

| 対象 | v1 の処理上限 |
| --- | --- |
| エンベロープのファイル長 | 256 MiB |
| 復号後 payload の UTF-8 バイト長 | 180 MiB |
| 投稿数 | 100,000 件 |
| 添付数 | 10,000 件 |
| 添付のバイナリ長 | 1 件 5 MiB、合計 120 MiB |
| 本文長 | 1 件 100,000 UTF-16 code unit |
| 投稿 ID・添付 ID | 1 件 128 UTF-16 code unit |
| タグ | 1 投稿 256 個、1 個 128 UTF-16 code unit |
| 怒り値 | 1 件 1,000,000 桁 |

作成・復元の両方に適用する処理上限であり、一部を省略せず失敗を表示する。処理中に複数のバッファやJSONを持つため、上限未満でも端末のメモリによって失敗し得る。小さいiPhone・Android端末を含めた実機検証は未実施である。分割形式などへの変更は別バージョンとして設計する。

### 既存データを破壊しない復元

1. ファイルを読み、サイズ・エンベロープ・対応バージョン・KDF パラメーターを検証する。この段階では IndexedDB を変更しない。
2. パスワードから鍵を導出し、AES-GCM の認証まで成功してから JSON を解釈する。
3. 全投稿・タグ・画像を検証する。ID の一意性、参照先、日時、カウント、Base64、MIME type、長さ、ダイジェストを確認する。未知のスキーマには明示的な移行実装がある場合だけ対応する。
4. 復元件数・既存件数・重複・競合・必要容量をプレビューする。既定は「既存を保持して追加」。既存データを全削除して置き換える機能を初期の復元には設けない。
5. 同一 ID・同一内容は重複として追加しない。同一 ID・異なる内容は既存を残し、復元側へ新しい ID を割り当てて画像の参照も付け替える。画像 ID の競合も同様に処理する。判断は実際の書き込みトランザクション内で再確認する。
6. 利用者がプレビューを確認してから、投稿と画像を一つの読み書きトランザクションで追加する。容量不足や書き込み失敗は全体をロールバックし、既存データを保持する。
7. トランザクションの commit を確認してから成功を表示する。タブの終了やキャンセルは完了扱いにしない。

競合した復元コピーには、元の投稿と画像の内容から導出した識別子を使う。同じバックアップの再復元では、このコピーも含めて内容と画像の全バイトを照合し、重複を防ぐ。コピーを編集した場合も編集済みの記録を残す。同じスナップショット内の別の投稿 ID はそれぞれ独立した記録として扱い、元投稿と復元コピーの片方を欠落させない。

引用・返信の関係を比較と識別子に含め、親から子の順に最終IDを確定して参照も付け替える。関係のない旧投稿の識別子生成は維持する。完全バックアップ内に参照先がない場合は削除済みと扱い、そのIDが既存の別投稿と衝突した場合は安定した欠落先IDに置き換え、無関係な投稿へ誤接続しない。引用・返信の同時指定、自己参照や参照の循環を検証で拒否する。

破損、誤パスワード、未知バージョン、不正な参照、容量不足、競合中の編集を必ず失敗系テストに含める。復元中に読み取った内容を HTML として表示しない。

### リマインダー

7日・30日・オフを選べる。前回の利用者による保存確認日時、未確認の場合は最古の投稿日時から期間を判定し、起動・画面復帰時にアプリ内で案内する。投稿がない場合は出さない。PWAを閉じている間の定期実行、ファイルの自動保存、通知権限、パスワードの保存は必要としない。
